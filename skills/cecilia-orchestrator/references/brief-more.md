# Briefing — background, splitting, re-launch, anti-patterns

Part of `agent-briefs.md`; open when splitting a role, re-launching after Cecilia answers, or when a brief went wrong.

## 1. Why no summaries

Cecilia's rule: context passes through files only. A summary in a brief is a second copy of the truth
that nobody updates, and the agent that believes it produces work traceable to nothing. `common/workspace.md`
already guarantees that any agent can pick up from the files alone — the brief only has to say *which*
files. So:

- **Allowed:** paths, ids, branch/PR names, scope boundaries, Cecilia's recorded decisions with their
  date and source, the return contract.
- **Not allowed:** "the API returns an envelope with…", "the plan says B-02 depends on B-01",
  "the design chose Postgres". If the agent needs it, it reads it.

v20: every brief is generated by `workflow.py brief` and **filled** — header line, mode, flow, scope, lane,
branch + start SHA, allowed A3, files to read, report path — and ends with the ≤ 15-line return contract
(`agent-briefs.md` §5) and `## Rules (must follow)`. The rules are the one text a brief embeds: they are
Cecilia's, short, and must be in the agent's context before its first write.

One line every brief carries: *"Nothing in this brief describes file content. If anything here
contradicts a file, the file wins — follow the file and say so in your report."*

## 4. Splitting a role into several agents

The workflow option Cecilia chose sets how many agents each role gets (`units`, one tester per test lens,
one reviewer per review lens). When an option splits a role, split so that:

- **Disjoint file scope.** Two agents must never be able to write the same file. If the plan's
  batches share files, they cannot be split — say so and keep one agent. (A `competing` split is the
  one exception: its units build the same seam on separate branches and are never merged together.)
- **Split along the plan's own seams**: by batch for dev and test, by stage or service for design,
  by target for review. Never split "half the batch each".
- **Each split agent is its own unit** in the wave computation (`waves.md` §1 step 1), with its own
  scope, its own worktree if it writes code, its own brief and its own run-log row.
- Whether they share a wave is decided by the algorithm, not by the split: three `review` agents on
  three targets share one wave, three `dev-be` agents in one module never do, because their write
  sets collide in the router and the DI module every time.
- Step N's brief may point at step N−1's report path, never at its content.

Say the trade-off to Cecilia once: more agents = cleaner context and a smaller blast radius per
agent. Whether it also saves time depends entirely on whether they land in one wave — say which, and
do not let a split read as a promise of speed the grouping does not support.

## 6. Re-launch after Cecilia answers

A relaunched role gets a **fresh agent** with the same brief plus one extra block, placed after
block 4:

```
DECIDED BY CECILIA (<date>) — these are settled, do not re-ask:
1. <question> → <answer>
2. ...
Recorded in: tensura/reports/<TASK>/orchestration-<TASK>.md §4.
Record them in the place your skill specifies (decision log / plan / report) as
"decided by: Cecilia, <date>".
```

Keep the same model unless Cecilia changed it. Add nothing else — in particular, do not summarize
what the previous agent did; its report path in block 4 covers that.

## 7. Anti-patterns

| Wrong | Right |
|---|---|
| Pasting doc or plan content into the brief | Paste the path |
| "Use your judgement if the docs are unclear" | "Stop at the gate and return the question" |
| Launching a role without naming its scope | Scope block with ids |
| Letting an agent create its own working folder | Block 2, the workdir it was given |
| Two agents live at once "because they don't overlap" | Compared write sets, or they are in different waves |
| A worktree brief that does not say where the report goes | Block 2.1, both workdirs, spelled out |
| Relaying questions the agent marked dependent as one gate | The agent sorted them; keep the sort |
| Re-sending a question Cecilia already answered | Check the run log first (`core.md` §5.1) |
| A brief with no return contract | §5 verbatim, every time |
| Asking a role to paste its report into chat | Read `tensura/reports/<TASK>/<role-short>.md` |
| Relaying push/PR as a question | Collect the commands into the one final copy-paste block for Cecilia |
